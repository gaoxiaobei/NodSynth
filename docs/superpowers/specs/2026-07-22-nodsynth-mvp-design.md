# NodSynth MVP 设计规范

日期：2026-07-22
状态：已完成设计评审，待用户审阅书面规范

## 1. 产品目标

NodSynth 是一个节点式软件合成器。用户像使用 ComfyUI 一样，在画布上连接振荡器、包络、滤波器和输出等节点，构建可由 MIDI 演奏的合成器音色。

长期目标是提供 Linux、Windows 和 macOS 独立应用，并以 VST3 为主要插件格式、以 AU 为 macOS 补充格式。项目采用开源模式，并最终允许第三方开发者独立发布、安装和升级节点包。

首个 MVP 聚焦 Linux 独立应用。它的成功标准是：用户能够从节点构建一个 16 声部减法合成音色，实时演奏和编辑，并在保存、重新打开工程后恢复声音及画布状态。

MVP 不包含 DAW 插件、多轨录音、混音工作站、外部音频效果器、在线扩展商店或正式发布的第三方 SDK。

## 2. 技术路线

项目采用 C++ 与 JUCE 构建分层的模块化单体。JUCE 负责跨平台应用生命周期、音频/MIDI 设备以及未来的插件外壳；图模型、编译器和 DSP 运行时保持独立，不能依赖 JUCE UI 对象。

选择该路线的原因是：

- 独立应用和未来 VST3/AU 可以复用核心与界面。
- C++ 适合低延迟实时 DSP，跨平台插件工具链成熟。
- 单语言 MVP 的构建、调试和数据流比 Rust/C++ 混合方案简单。
- 原生 UI 避免嵌入 Web 前端在插件宿主中的焦点、缩放、体积和通信问题。

第三方节点的长期方向是原生动态库。节点包分别提供 Linux、Windows 和 macOS 二进制，并通过稳定 C ABI 接入。C++ SDK 只作为 C ABI 的便利封装，不把 C++ ABI 作为兼容契约。更远期可以为控制逻辑增加 WebAssembly，但它不属于 MVP。

## 3. 总体架构

系统划分为编辑状态和实时运行状态：

```text
Standalone App / Future Plugin Shell
                 │
              Editor UI
                 │ commands / snapshots
                 ▼
           Graph Document
                 │ validate + compile
                 ▼
           Graph Compiler ───── Node Registry / C ABI
                 │ immutable Execution Plan
                 ▼ atomic swap at audio-block boundary
          Realtime DSP Runtime
                 │
          JUCE Audio / MIDI
```

UI 只修改 `Graph Document`。结构变化由后台线程验证并编译成完整、不可变、已预分配的 `Execution Plan`。编译成功后，运行时在 audio block 边界原子切换计划；编译失败时保留旧计划继续发声，并把结构化错误返回编辑器。

音频线程只能读取执行计划、处理预分配的节点状态和缓冲区、消费无锁参数/MIDI 数据。它不得执行堆分配、文件 I/O、动态库加载、互斥锁等待或日志格式化。

## 4. 模块边界

项目按职责拆分为以下独立构建目标：

- `nod_model`：节点和端口 schema、Graph Document、编辑命令、撤销/重做和序列化。它不依赖音频设备或 UI。
- `nod_compiler`：类型检查、环检测、作用域检查、拓扑排序、声部展开及缓冲区规划。
- `nod_runtime`：不可变执行计划、voice allocator、参数通道和实时 audio block 处理。
- `nod_nodes`：内置节点实现。每个节点通过注册表接入，图引擎不依赖具体节点类。
- `nod_extension_api`：稳定 C ABI 数据结构、版本协商和节点生命周期。MVP 用它验证内置注册边界，但不对外发布 SDK。
- `nod_ui`：节点画布、检查器、搜索、设备设置与错误展示，不包含 DSP 算法。
- `nod_app`：JUCE 独立应用、音频/MIDI 设备和应用生命周期。
- `nod_plugin`：未来插件目标。MVP 不构建，其他核心模块不得依赖它。

每个模块通过公开接口通信；任何模块的内部实现都可以在不改变其契约的情况下替换。

## 5. 节点模型

同一个节点概念分成三类对象：

### 5.1 Node Definition

`Node Definition` 是注册与兼容契约，包含：

- 全局稳定的 type ID，例如 `org.nodsynth.oscillator.analog`。
- schema 版本、显示名称、分类和来源。
- 输入/输出端口 schema。
- 参数 schema，包括稳定参数 ID、单位、范围、默认值、缩放曲线和调制能力。
- `PerVoice` 或 `Global` 作用域能力。
- 创建和销毁 DSP 状态、prepare、process、reset 等回调。

显示名称不参与连接、保存或兼容判断。

### 5.2 Node Instance

`Node Instance` 存在于 Graph Document 中，包含工程内唯一 UUID、type ID、节点版本、参数值、私有序列化状态及画布位置。它不持有实时 DSP 指针，可以被复制、撤销和序列化。

### 5.3 DSP Runtime Instance

图编译器根据 Node Instance 创建实时实例。它只包含预分配状态、缓冲区索引、参数平滑器和处理回调，不包含 UI、JSON 或文件系统对象。

振荡器、ADSR 和逐音符滤波器等节点属于 `PerVoice`，最多拥有 16 份实时状态。主增益和最终输出等属于 `Global`。显式的 `Voice Mix` 节点是从逐声部图进入全局图的唯一边界。

## 6. 端口、参数与连接规则

MVP 提供四种强类型端口：

- `Audio`：单声道或立体声 sample buffer，只能连接 Audio 端口。声道数必须相容；声道转换使用显式节点。
- `Control`：数值控制信号，可表示 block 常量、平滑 ramp 或逐 sample buffer。编译器根据上游变化率选择表示，不改变用户可见类型。
- `Gate`：包含 sample offset 的开/关边沿，用于包络与触发。
- `Note`：包含音高、力度、MIDI channel 和 note ID 的逐声部音符数据。

不同类型不能隐式连接。`Note to Frequency`、`Control to Audio` 和声道转换等行为必须由显式节点完成，保证图的语义可见。

可调制参数同时具有基础值和可选 Control 输入。接线不会覆盖旋钮值；节点 schema 定义如何将归一化调制、调制深度和基础值映射到实际单位。最终参数在送入 DSP 前执行平滑和范围限制。

普通连接必须构成有向无环图。需要反馈时必须经过显式 `Feedback Delay` 节点；该节点引入确定的最小延迟，从而切断当前处理周期的依赖。编辑器在建立非法环路时立即拒绝连接并说明原因。

## 7. 图编译与实时执行

结构编辑和参数编辑使用两条路径。

### 7.1 结构编辑

添加/删除节点、改变连线或改变影响端口布局的配置时：

1. UI 对 Graph Document 应用可撤销命令。
2. 后台编译器创建一致快照。
3. 编译器验证 type ID、端口类型、作用域、环路和节点版本。
4. 编译器完成拓扑排序、最多 16 声部的状态规划及缓冲区复用规划。
5. 所有节点状态和缓冲区在切换前完成分配与 prepare。
6. 音频线程在 block 边界接收新执行计划。
7. 新计划在切换点接收当前仍按住的音符快照，并重新触发对应声部；旧计划和新计划交叉淡化 10–20 ms，随后由非音频线程回收旧计划。

切换前，编译器必须计算所需状态和缓冲区内存。若超出预算，则拒绝新计划并保留旧声音。

MVP 不要求跨结构编辑迁移振荡器相位、滤波器延迟线或包络进度等内部 DSP 状态；新计划会从起点重新触发仍按住的音符，短交叉淡化负责避免明显 click。未改变结构的参数编辑不会触发该重建。

### 7.2 参数编辑

UI 或未来 DAW host 提交归一化参数事件。事件经无锁单生产者/单消费者通道进入实时运行时，并由节点参数平滑器产生逐 sample 值。队列满时允许合并同一参数的中间值，但必须保留最新值；该情况通过非实时遥测记录。

### 7.3 MIDI 与复音

MIDI 事件保留其在 audio block 内的 sample offset。Voice Allocator 将 Note On/Off 分配给最多 16 个声部，并生成 Note 与 Gate 数据。

声部耗尽时按确定规则抢声：优先选择已处于 release 阶段且最旧的声部；若没有，再选择最旧的活跃声部。被抢声部使用极短淡化抑制 click。每个声部执行 PerVoice 子图，随后由 `Voice Mix` 汇聚并执行 Global 子图，最终输出立体声音频。

## 8. 编辑器体验

主界面采用“节点画布 + 右侧参数检查器”：

- 左侧为可搜索、按分类组织的节点库。
- 中间画布用于选择、框选、移动、复制、删除、连线、断线、缩放和平移。
- 节点卡片保持紧凑，展示关键参数和端口。
- 右侧检查器展示选中节点的完整参数、调制深度、type ID、版本和来源。
- 拖线时只高亮类型兼容的端口。
- 顶部状态区显示图编译状态、错误、活跃声部数和 DSP CPU 占用。
- 设置界面允许选择音频设备、采样率、buffer size 和 MIDI 输入。
- 外部 MIDI 键盘与内置屏幕键盘都可以触发音符。

首次启动加载一个可发声的默认 Patch。应用另附两到三个示例 Patch，帮助用户验证音频/MIDI 配置并理解基本连线。

## 9. MVP 内置节点

MVP 内置节点保持最小但完整：

- `MIDI Input`：输出 Note、Gate、Velocity 和 Pitch Bend。
- `Note to Frequency`：将 Note 显式转换为频率 Control。
- `Oscillator`：支持 Sine、Triangle、Saw 和 Square。
- `ADSR`：由 Gate 驱动并输出 Control 包络。
- `State Variable Filter`：MVP 对用户仅提供 Low-pass 模式。
- `Gain`：Audio 输入和可调制增益。
- `Add`、`Multiply`、`Scale/Bias`、`Mix`：基础运算和调制组合。
- `Voice Mix`：PerVoice 到 Global 的作用域边界；MVP 接收每声部单声道 Audio，求和并以中央声像产生立体声输出。
- `Audio Output`：立体声最终输出与安全增益处理。
- `Feedback Delay`：MVP 必须实现至少一个 audio block 的确定延迟，以支持安全反馈并验证环路语义。

MVP 不包括 LFO、Noise、示波器、Unison、琶音器、宏旋钮、节点分组、合唱、延迟效果或混响。这些节点可以在核心稳定后独立增加，不需要修改图引擎。

## 10. 工程文件与版本兼容

工程使用人类可读的 JSON。顶层包含：

- 文件格式版本与写入该文件的应用版本。
- 可选、非强制的采样率和 buffer size 提示；物理设备 ID 属于应用偏好，不写入可分享工程。
- 节点实例、参数、私有状态及画布位置。
- 由源节点/端口 ID 和目标节点/端口 ID 表示的连接。
- 画布缩放、视口和注释等展示状态。
- 扩展依赖 ID、版本范围及来源信息。

加载流程先解析到中立 Graph Document，不立即创建 DSP。节点版本落后时，由提供该节点的扩展执行逐版本迁移，例如 v1 → v2 → v3。

缺失节点或无法迁移时，加载器创建 `Missing Node` 占位符，并原样保留未知参数、私有状态、端口标识和连接。安装兼容扩展后可以原位恢复。含 Missing Node 的图可以编辑和再次保存，但不能编译为完整执行计划；若应用中已有可运行计划，则继续使用旧计划，否则保持静音并显示错误。

解析器保留它不理解的节点私有字段，避免较旧宿主无意破坏较新扩展数据。保存采用同目录临时文件加原子替换，写入失败不覆盖上次成功的工程。

未来 VST3/AU 的宿主状态复用同一文档模型，可以增加压缩封装，但不能另造不兼容格式。

## 11. 扩展加载与安全边界

MVP 中的内置节点也必须通过 Node Registry 注册，以验证未来扩展所需的边界。正式第三方 SDK 和扩展安装器延期到后续里程碑。

未来节点包包含 manifest、扩展 ID/版本、兼容的宿主 ABI 范围、节点 schema 以及各目标平台动态库。动态库只在启动或用户明确执行刷新时由非音频线程加载。

单个扩展加载失败不能阻止应用打开；注册表记录失败原因，并让依赖它的节点显示为 Missing Node。由于原生节点与宿主同进程运行，MVP 和首版 SDK 不承诺崩溃隔离。扩展管理界面必须明确展示来源、版本和原生代码信任提示。

## 12. 错误处理

图相关错误采用结构化诊断，至少包含错误代码、严重程度、节点 UUID、端口 ID 和用户可读说明。主要行为如下：

- 非法端口连接和无显式延迟的环路在编辑时被拒绝。
- 后台编译失败或资源超限时，旧执行计划继续运行。
- 首次加载且没有可执行计划时，应用保持静音并显示可定位错误。
- 音频设备断开时停止输出但保留工程，允许用户重新选择设备。
- 最终输出检测到非有限值时，将受影响 block 安全静音并通过非实时通道报告。
- `Audio Output` 提供安全幅度限制，避免失控反馈产生危险输出；该限制不代替节点自身的数值稳定性测试。

音频回调不得抛出异常到宿主。实时节点的失败只能转换为静音、安全值或预定义错误状态，再由非实时线程呈现。

## 13. 测试与质量门槛

### 13.1 单元测试

- 端口兼容与拒绝规则。
- 环检测及经过 Feedback Delay 的合法反馈。
- PerVoice/Global 作用域检查。
- 拓扑排序、缓冲区规划和资源上限。
- 参数映射、范围限制和平滑。
- voice allocation、Note Off 和确定性 voice stealing。

### 13.2 DSP 测试

使用固定输入离线渲染，验证振荡器频率/波形、ADSR 时序、滤波稳定性、Gain 与运算节点。测试覆盖常用 sample rate 和多种 block size，并检查输出不包含 NaN/Inf。

浮点比较使用明确容差；不对跨 CPU 架构的逐 bit 相同作保证。

### 13.3 工程测试

- JSON 保存/加载往返保持语义一致。
- 原子保存失败不破坏旧文件。
- 未知字段和 Missing Node 数据得到保留。
- 节点逐版本迁移与扩展恢复正确。

### 13.4 集成与实时压力测试

持续发送 MIDI 的同时增删节点、改变连线和快速调参，验证：

- 无崩溃、死锁或音频线程堆分配。
- 无 NaN/Inf 和明显结构切换 click。
- 编译失败时旧图继续发声。
- 16 声部抢声行为可重复。
- 保存并重载标准 Patch 后离线渲染结果在容差内一致。

性能基线为 48 kHz、128 samples、16 声部和标准减法合成 Patch。开发机 Release 构建持续运行 10 分钟不得发生 xrun，并记录硬件、编译配置及 audio callback 耗时分位数。常态下回调耗时目标低于单个 block 时限的 50%，为结构切换的短暂双图执行留出余量。

CI 在 Linux 运行完整测试和实时安全检查；Windows 与 macOS 至少执行编译和不依赖设备的核心测试。MVP 的发布验收只要求 Linux，但三端编译失败视为架构回归。

## 14. MVP 验收场景

在一台 Linux 开发机上，用户可以：

1. 启动 NodSynth 并选择音频和 MIDI 设备。
2. 创建 `MIDI Input → Note to Frequency → Oscillator → Filter → Gain → Voice Mix → Audio Output` 图。
3. 使用 ADSR 驱动 Gain，并能用控制运算节点调制 Filter cutoff。
4. 用 MIDI 或屏幕键盘演奏最多 16 个同时音符。
5. 在持续演奏时改变参数、添加/删除节点和重新接线，不发生崩溃或明显爆音。
6. 遇到非法类型、非法环路或不可编译图时获得具体错误，且上一个有效图继续发声。
7. 保存工程、退出应用、重新打开并恢复相同的节点、参数、连线、布局和可演奏声音。
8. 在标准压力 Patch 下满足第 13 节的实时与性能门槛。

完成上述场景即代表 MVP 达标。VST3/AU、三平台安装包、正式第三方 SDK 与节点商店进入后续独立设计和实施周期。
