## 1. 两个产品目标

**NodSynth 是可独立使用、可嵌入、可作为插件加载的合成器；编曲套件是以无界面 DAW 核心为基础，由 AI、命令行和图形界面共同操作的音乐制作系统。**

合成器负责“音符和参数如何变成声音”；DAW 核心负责“哪些轨道在何时演奏、使用什么乐器、如何路由和导出”。AI 负责提出和修改音乐内容，通过稳定编辑接口操作 DAW，不直接操作音频线程或依赖模拟鼠标操作。

下一版本的成功场景：导入一首多轨 MIDI，为旋律分配 NodSynth、为另一轨分配外部合成器，执行一条命令，得到同步的混音、分轨和可追溯渲染报告；AI 能修改指定小节的音符并重新渲染。

## 2. 当前基线与实际缺口

Windows 合成器 MVP 已完成，历史验收记录保留在 [MVP 历史](history/MVP-2026-10-04.md)。本次通过源码核对范围，没有重跑历史验收。

| 当前实现 | 距离编曲用途的缺口 |
|---|---|
| `nod_render --midi` 可把 SMF 和已保存 Patch 写成流式 WAV | 仍是单音色实例；没有歌曲模型、多轨混音或外部合成器 |
| `Engine::process` 接受块内事件 | 没有歌曲时间轴、速度图、轨道映射、宿主 transport |
| `MidiType` 有 Note On/Off、sustain、all-notes-off/all-sound-off | 没有通用 CC、pitch bend、program change 的完整表达与能力报告 |
| `ProjectDocument` 保存图和视口 | 是合成器音色工程，不是 DAW 歌曲工程 |
| 单引擎、16 声部、立体声输出 | 没有多乐器实例、轨道混音、总线、插件延迟补偿 |
| 当前 WAV 工具将整段音频保存在内存 | 长曲需流式写入、RIFF 大小检查和可选 RF64；读 WAV 也不能假设固定 44 字节头 |
| 运行时有界事件缓存，超限会 panic | 离线渲染必须预检密度并明确失败或扩容准备，不能把丢音当成功 |

## 3. 分层与依赖

```text
AI 编曲客户端        CLI          DAW 图形界面
       └──────────────┼──────────────┘
               工程查询 / 编辑命令 API
                      ↓
       SongDocument（音符、片段、轨道、速度、自动化）
                      ↓
        时间调度 / 混音与路由 / 离线渲染任务
                      ↓
          Instrument / Effect 内部处理接口
          ├── NodSynth 内嵌适配器 → 现有核心
          ├── 外部命令行渲染适配器 → 对齐后的音频 stem
          └── VST3 宿主适配器 → 第三方乐器和效果器

现有 NodSynth 核心 → 独立应用 / CLI / 未来 NodSynth VST3 外壳
```

先在当前仓库增加独立构建目标，复用 C++20 核心，不立即拆仓库或改写 Windows 界面。套件不得成为 `nod_runtime` 的依赖。现有模块继续属于 NodSynth；歌曲模型与宿主模块保持不含合成器节点类型的通用接口。名称暂用 `nod_song`、`nod_midi`、`nod_audio_io`、`nod_render_core`、`nod_host`，套件 CLI 暂称 `nod`。

合成器内部 DSP 节点插件与 DAW 乐器/效果器插件是两个层次。近期优先标准乐器插件互通，不冻结自定义节点动态库 ABI。

## 4. 工程和时间模型

### 三种独立资产

- **Patch**：复用现有音色工程，保存节点、参数和布局；在文档层澄清其名称，不强制破坏现有文件格式。
- **Song**：独立版本化格式，包含稳定 track/clip/note ID、音符、速度图、拍号、自动化、乐器实例、音色引用、增益/声像、路由和资源表。
- **RenderJob**：引用不可变 Song 修订，指定区间、采样率、块长、尾音策略、输出格式、分轨、随机种子和依赖快照；不把导出设置混进乐器状态。

第一版支持 MIDI 片段和乐器轨，预留音频片段与效果器，但不提前实现录音、时间伸缩等完整 DAW 功能。资源使用工程相对路径与内容哈希；导出可搬移工程时收集 MIDI、Patch、采样和插件状态。插件二进制不打包，缺失依赖明确报错。

### 时间与 MIDI 语义

1. Song 保存有理数拍位置/时值或等价无损 tick 表达；导入保留原始 PPQ，避免固定低分辨率网格量化。采样位置使用 64 位整数。
2. 集中维护 tempo map，将绝对音乐位置积分转换为绝对 sample，再取块内 offset；不逐块累加四舍五入误差。拍号影响小节显示，不改变 tick 的时长定义。
3. P1 支持 SMF type 0/1、PPQ、tempo/time-signature 元事件、running status、Note On velocity 0。无 tempo 默认 120 BPM，无拍号默认 4/4；type 2 和 SMPTE division 首版明确拒绝。
4. MIDI track、channel 与合成器实例不是同一概念。导入按源 track/channel 提供显式映射；type 0 也可分成多个乐器轨，不能把多轨都送到一个音色实例。鼓轨不自动套用旋律音色。
5. 同刻事件保留稳定来源顺序（tick、源轨序号、轨内序号）；生成的同音重触发约定 Off 在 On 前。不同轨道同刻冲突 tempo 按明确优先规则处理并诊断。
6. 保留不支持的 CC、program change、SysEx 和元数据，报告原始位置及类型；默认不静默丢弃影响声音的事件。导入可以保留后继续编辑，渲染严格模式拒绝不支持语义，宽松模式需显式开启并报告。
7. sustain、重复同音、音符配对、片段末尾仍按住的音符均需明确规则。导出尾部释放 sustain/音符，再渲染尾音；不得在音乐结束点立即切断包络。

## 5. 两条互通路线

### NodSynth 成为别人的乐器

NodSynth VST3 外壳复用核心，接收宿主 MIDI、transport 与参数事件，输出音频并保存/恢复 Patch 状态。与 CLI 共享音色语义。先无专用编辑器可运行，之后接入或重构界面；现有 Win32 窗口不能直接假定可作为跨平台插件编辑器复用。

这是让 NodSynth 进入现成 DAW 的最短产品路线。VST3 外壳是插件“客户端”，下面的 VST3 宿主是另一项工作，不能把完成其中一个当作完成另一个。

### 套件加载其他乐器

首版联合渲染先支持：NodSynth 内嵌实例 + 一个真实外部离线渲染器。后续实现通用 VST3 宿主。

| 接入方式 | 近期用途 | 限制 |
|---|---|---|
| 内嵌 NodSynth | 多轨、多实例及统一时间验证 | 只覆盖自家合成器 |
| 外部 CLI 渲染器 | 快速交付不同合成器联合离线渲染；首个候选为 FluidSynth + 用户提供的 SoundFont | 需固定版本并实测 CLI 行为；不等价于通用插件宿主，不支持实时交叉路由 |
| VST3 宿主 | 接入用户现有乐器/效果器，提供 transport、自动化和延迟补偿 | 需 SDK/工具链验证、插件扫描、状态恢复及兼容性测试 |

CLI 适配器声明：支持的 MIDI 事件、采样率、起点规则、尾音、状态/随机种子、最大时长、退出码和输出格式。通过参数数组启动进程。输入使用已解析的歌曲时间或包含同一 tempo map 的规范 MIDI；各 stem 必须有公共零点，禁止擅自裁掉开头静音。拒绝未声明的采样率/声道差异，或执行明确的转换。报告非确定性，不能承诺第三方插件跨机器逐位一致。

VST3 宿主先支持 Windows x64、无界面离线立体声乐器和串联效果链。扫描和渲染放入工作进程；超时、崩溃、缺失插件或加载状态失败令任务失败，默认不生成“成功但少一轨”的混音。插件通过稳定 class ID、版本和状态定位，不按显示名称猜测。

引入前做 SDK 构建与许可证核对；当前 LLVM-MinGW 可构建现有应用，不代表已满足所选 SDK/封装库的支持条件。是否用 JUCE 根据宿主与插件外壳原型决定，避免为此先重写全部 UI。

## 6. 统一处理和渲染契约

内部 Instrument/Effect 接口至少包含能力查询、prepare/reset/process、状态保存恢复、参数枚举、延迟与尾音查询。处理上下文包含绝对 sample、块长、采样率、播放位置、tempo/拍号，以及有采样偏移的 MIDI/参数事件。内部接口先可演进，不作为公共二进制 ABI。

- 所有轨道共享采样率、时间原点与渲染区间，各实例独立状态与复音预算。离线按同一时间轴处理，初版串行。增益是线性振幅。声像为等功率：-1 极左，0 中央（每声道 cos(π/4)），+1 极右。轨道增益自动化存在时取代静态增益，并按采样位置在相邻点之间线性插值。分轨是增益/声像之后、主效果之前的立体声；无主效果时混音等于分轨求和。
- 从零渲染是确定基线。局部区间渲染默认从零预跑或使用经验证的状态检查点，再裁切；只 seek 到小节而不恢复持续音、控制器和效果尾音会产生错误。
- 初版路由为轨道 → 主输出，增益/声像规则固定且文档化。后续加入无环总线与发送、插件延迟补偿；暂不支持反馈路由和侧链。
- 输出 float32 WAV；峰值超限报告，不逐轨自动归一化。限幅、响度归一化作为显式导出选项。初版 stems 定义为轨后增益/声像、主效果前；共享效果返回单列，不宣称带非线性主效果的 mix 等于 stems 相加。
- 尾音支持固定长度及阈值检测加最长上限，达到上限报告截断。外部 stem 补齐到相同长度；不得通过裁切掩盖延迟问题。
- 流式写入临时输出，成功后提交整套产物与 manifest；失败输出保留诊断且不伪装为成品。首版对超过 RIFF 上限明确拒绝，后续再加 RF64。
- 报告记录输入哈希、工程修订、适配器/插件版本、采样率、帧数、延迟补偿、警告、输出哈希和性能。缓存键涵盖全部声音依赖；未声明确定性的后端默认不跨任务复用缓存。

## 7. AI 与 CLI 契约

AI 首先需要可查询和编辑的音乐数据，而不是一个单独的聊天窗口。同一套命令供人写脚本、AI 调用和未来 UI 使用。

P1 已可执行：

```sh
nod_render --midi melody.mid --patch lead.json --output lead.wav --tail-seconds 3
```

`nod_render` 的退出码：1 输入或格式，2 缺失音色或编译失败，3 渲染被拒绝，4 输出 I/O。修订冲突预定为 5，随歌曲修订实现。`--json` 时标准输出只放报告，说明走标准错误。

P2 与 P3 已可执行。NodSynth 轨使用 Patch；FluidSynth 轨使用 SoundFont，并把 `fluidsynth` 可执行文件交给 `--fluidsynth`：

```sh
nod song import-midi song.mid --output song.nodsong.json
nod song validate song.nodsong.json --json
nod song apply song.nodsong.json --commands edits.json --expect-revision 12
nod render song.nodsong.json --output mix.wav --stems stems --report render.json
```

接口支持查询音轨/音符/音色能力、插入和修改片段、改变乐器映射、参数自动化、渲染指定区间及音频分析。命令有 schema 版本、稳定对象 ID、request ID、预期工程修订和事务边界；冲突明确返回，重试不会重复添加音符。批量编辑可预览 diff、撤销和重做。

`stdout` 在 `--json` 模式只输出结构化结果，日志/进度走 `stderr`；错误包含 code、对象位置、message、是否可重试。规定稳定非零退出码类别：输入/格式、缺失依赖、渲染失败、输出 I/O、修订冲突。首次实现时固定具体数值并测试。

第一版 AI 场景限定为“读工程 → 按要求修改指定小节 → 校验 → 导出 MIDI → 渲染试听 → 查看峰值/响度/静音等分析”。音乐质量由试听和用户反馈评价，响度等指标不代表编曲质量。模型供应商通过客户端适配，不把某个服务写进音频引擎。服务式 API/MCP 在 CLI 契约稳定后再封装。

## 8. 开发顺序与验收

### P1：让 NodSynth 真正可用于命令行演奏

**范围：SMF + 已保存 Patch → WAV。** 不需要先实现完整 Song 或插件宿主。

1. `nod_midi`：SMF 解析、tempo map、稳定事件排序、track/channel 选择、能力诊断；限制恶意或损坏文件的长度、事件数和 varlen。
2. `nod_render_core`：抽取现有 main 中的准备/处理循环；接入 `loadProject`，让测试和 CLI 共用入口，保留旧演示/soak 模式。
3. 增加离线事件调度、尾音处理和流式 WAV 输出；移除演示用 30 秒上限，改为显式时长/资源预算。首版单 Patch 可以选择或合并通道，但帮助文档不得宣称会自动还原多音色 MIDI。
4. 添加结构化 inspect/validate/report；补齐 pitch bend、CC64 及 CC120/123 的端到端测试。其他 CC/program 按能力策略处理，不宣称 General MIDI 完整支持。

验收：type 0/1、变速、非 480 PPQ、running status、重触发、sustain、跨块事件、损坏文件有 fixture；44.1/48 kHz 与不同块长的事件落点相差不超过 1 sample。带滤波的保存音色可以正确加载；渲染超过 30 秒；尾音不挂音；超密事件明确失败、不静默 panic 成功；内存不随整首 PCM 长度增长。

### P2：无界面 DAW 核心与多轨混音

依赖 P1。实现 Song v1、MIDI 导入/导出、轨道/片段/乐器映射、多 NodSynth 实例、增益/声像、mix/stems 和统一报告。第一版仅从零完整渲染，自动化先覆盖轨道增益，再扩展采样精确的乐器参数接口。

验收：至少 3 轨不同音色、变速和延后进入的片段；公共起点一致；无主效果时 stems 按约定求和与 mix 在容差内一致。保存重载和 MIDI 往返保留承诺支持的音乐语义，缺失 Patch 拒绝渲染。

### P3：完成不同合成器联合离线渲染

依赖 P2。实现外部渲染协议及一个真实适配器，默认候选 FluidSynth；若用户实际使用另一款可无界面渲染的合成器，替换首个适配器而非更改歌曲模型。具体后端与测试资产在实施前确认。

验收：一轨 NodSynth + 一轨真实外部合成器，经同一 Song 一次导出 mix/stems；用已知脉冲/节拍事件验证对齐和漂移，检查变速、尾音、采样率差异、进程失败和超时。只有两份文件相加但没有时间语义验证，不算联合渲染完成。

### P4：标准插件互通

两项独立交付：P4a NodSynth VST3 乐器（P1 后即可推进）；P4b 套件 VST3 宿主（依赖 P2 的处理接口）。先做 SDK/工具链原型，再实现插件状态、transport、自动化、延迟补偿和工作进程。

验收：NodSynth 在一个现成 DAW 内接收 MIDI、保存重开状态、离线导出；套件加载至少一款真实第三方乐器和一款有效果延迟的插件，验证状态重载、时间同步、延迟补偿与崩溃报告。不以自家插件加载自家宿主作为唯一兼容证据。

### P5：AI 编曲可重复工作流

依赖 P2 的歌曲命令接口，联合渲染验收复用 P3/P4。实现事务编辑、修订冲突、能力查询、局部试听任务、音频分析和模型客户端适配。

验收：AI 读取现有 8 小节工程，保留旋律、修改低音并新增和声，输出可审阅编辑记录、MIDI、混音与分轨；用户可撤销，原工程可恢复。重复提交同一 request ID 不重复修改，渲染引用明确工程修订。

### P6：DAW 图形界面与套件扩展

基于同一 Song/API 做时间线、钢琴卷帘、混音器、transport 与 AI 面板；先播放和编辑，再加入录音、音频片段、拉伸、侧链等。自家效果器和其他合成器通过共同处理接口及标准插件外壳交付。多平台 UI 与安装发行另设验收，不阻塞 P1–P3。

## 9. 最近应开始的任务

先实施 P1，按“解析与时间转换 → Patch 加载与事件渲染 → 流式输出/尾音/报告”拆成三个可评审变更。随后 P2 与 P3 构成下一产品版本的硬门槛：**一份多轨 MIDI、明确的乐器映射、一条命令生成来自不同合成器的完整作品。**

暂不同时启动完整 DAW UI、插件商店、自定义节点 SDK和多模型编排。P4a 可在标准插件需求更紧迫时提前；如果外部目标只有 VST3、没有可靠 CLI，则用 P4b 替代 P3 的首个后端交付，保留相同联合渲染验收。
